# Codex Budget: подробное руководство

[← На главную](../README.md) · [Результаты проверок](test-report.md)

## Что мы хотим улучшить

Представьте небольшую задачу: исправить импорт таблицы. Агент может быстро найти нужную функцию, воспроизвести ошибку, внести правку и проверить её. А может несколько раз прочитать весь проект, повторить поиск, добавить необязательный рефакторинг и заново проверить то, что не менялось.

Оба пути иногда заканчиваются одинаковым результатом, но объём работы различается. Codex Budget задаёт ориентир: **получить согласованный результат с меньшим количеством лишних действий**, сохранив качество. Это набор инструкций, который другой экземпляр Codex читает при выборе навыка.

Навык не делает модель «дешевле» сам по себе. Его польза зависит от того, какие решения он реально изменит. Если агент и без него работает экономно, дополнительный выигрыш может быть небольшим.

## Почему всё началось с KV-кэша

[Статья на Хабре](https://habr.com/ru/articles/978498/) рассказывает, как модели избегают повторения некоторых вычислений. Внимание трансформера использует промежуточные представления, называемые keys и values. Их можно сохранять и повторно использовать. Именно это называют KV-кэшем.

Удобная аналогия — работа с большой инструкцией. Если её начало не изменилось, уже подготовленные данные об этом начале могут пригодиться снова. При этом новый ответ всё равно нужно построить; кэш не хранит готовый универсальный ответ на вопрос.

В API повторно используемый префикс должен совпадать с подходящей сохранённой записью. Кэширование зависит от модели, границ кэша и срока хранения. Сохранение чата само по себе не гарантирует попадания в кэш. Подробные правила меняются: источник для настройки API — [официальная документация](https://developers.openai.com/api/docs/guides/prompt-caching).

Практический вывод для этого проекта скромнее: нет смысла специально переписывать неизменившиеся инструкции, повторно читать тот же материал или раздувать запрос ради кэша. Однако скилл не управляет серверными записями кэша и не хранит их на ноутбуке.

## Чем подписочный лимит отличается от цены токенов

У API есть тарифы на категории токенов. Подписка Codex показывает доступную квоту. По [документации OpenAI](https://learn.chatgpt.com/docs/pricing), на расход влияют модель, сложность работы, контекст, рассуждения, инструменты и кэширование. Одной длины сообщения недостаточно для оценки.

Отсюда нельзя вывести правило «входные токены дешевле в десять раз → лимита хватит в десять раз дольше». Кроме обработки повторного ввода остаётся другая работа, а публичная цена API не задаёт полную формулу списания подписочной квоты.

Пять часов — длительность окна учёта, а не обещанные пять часов непрерывного общения. Для оценки нужно смотреть на доступные показания и время сброса именно своего аккаунта.

В этой версии намеренно нет таблицы «лучшая модель навсегда» или зашитого множителя скорости. При запросе рекомендаций агент должен свериться с текущими условиями и доступными настройками.

## Как меняется работа на практике

### Сначала определить готовый результат

Для задачи «почини импорт CSV» готовность может означать: пример пользователя читается, прежние допустимые файлы продолжают работать, ошибка покрыта проверкой. Полная переработка интерфейса и замена библиотеки обычно в этот результат не входят.

Это не повод задавать вопросы по каждой мелочи. Если намерение ясно, агент может выбрать разумную реализацию и выполнить задачу.

### Читать столько, сколько требуется

Агент сначала ищет место ошибки и связанные вызовы. Если обнаруживает зависимость, расширяет исследование. Он не обязан заранее загрузить все файлы или ограничиться одним файлом вопреки фактам.

Для больших логов полезно локально выделить ошибки и соседние строки. Для таблицы — подсчитать нужные показатели скриптом. Модель затем анализирует компактный результат. Запуск инструмента и анализ ответа всё равно являются частью агентной работы.

### Сохранять доказательства и менять гипотезу

Уже полученный результат проверки может быть полезен до тех пор, пока соответствующий код не изменился. После ошибки очередная попытка должна учитывать её причину.

Экономный процесс не означает «сделать меньше проверок любой ценой». Если проект требует полный набор тестов, его нужно запустить. Если изменение затрагивает важный механизм, дополнительное исследование может предотвратить гораздо более дорогую переделку.

### Выбирать настройки отдельно от текста скилла

При простом запросе может оказаться достаточно менее затратной модели или режима. При сложной диагностике сильная модель иногда быстрее приходит к правильному решению и требует меньше исправлений.

Навык может рекомендовать выбор. Сам файл `SKILL.md` не переключает текущую модель. Если пользователь явно выбрал модель и уровень рассуждения, скилл должен это сохранить.

## Что означает «замерить»

Допустим, перед работой счётчик показывает 35% использовано, после — 38%. Наблюдаемое изменение составляет **3 процентных пункта**. Это не «3% экономии».

Если интерфейс показывает остаток 65% → 62%, результат тот же. Сначала нужно определить направление счётчика. Пятичасовое и недельное окна анализируются отдельно; складывать их изменения нельзя.

Один такой замер отвечает на вопрос «как изменилось показание за этот интервал». Он не даёт точного счёта за конкретную задачу: в аккаунте могут работать другие чаты, данные могут округляться и обновляться с задержкой.

Ещё одна тонкость: агент снимает показание до окончания собственного ответа. Поэтому это контрольная точка, исключающая последующие действия и ещё не отражённый расход. В отчёте нужно обозначить именно такую границу.

Если окно успело сброситься, сравнение обычным вычитанием теряет смысл. Утилита из версии 0.2.0 распознаёт такие случаи и возвращает `inconclusive`.

## Как проверить экономию именно скилла

Для этого нужен отдельный сравнительный эксперимент:

1. Подготовить несколько похожих задач и одинаковые критерии готовности.
2. Сопоставить работу с навыком и без него при одинаковых настройках.
3. Учесть все попытки, исправления и качество результата.
4. Избегать параллельного расхода и сбросов окон.
5. Менять порядок запусков и фиксировать влияние кэша и повторного знакомства с задачей.

Такой эксперимент сам расходует квоту. Его стоит проводить, когда есть достаточно задач и ресурса, чтобы получить полезные данные. Повторять одну задачу десятки раз ради красивой цифры — плохой способ оценить практическую пользу.

В [текущем отчёте](test-report.md) отдельно показаны автоматические тесты утилиты и фактические наблюдения. Контролируемого сравнения экономии пока нет.

## Зачем отдельная утилита

`compare_usage.py` проверяет и сравнивает два подготовленных JSON-файла. Она различает used/remaining, окна, сбросы, пропущенные значения и ошибочные данные. Это избавляет агента от необходимости каждый раз заново писать арифметику и проверки.

Она не подключается к аккаунту, не получает ключи, не делает сетевые запросы и не записывает файлы. Сбор доступных показаний выполняется разрешённым инструментом отдельно. Формат входа и команды описаны в [методике](../skills/codex-budget/references/measurement.md).

Основной скилл работает и без Python. Его большая человеческая документация и тесты не входят в основной текст, который агент читает при каждом применении.

## Чего ожидать от первой версии с тестами

Это проверяемый рабочий процесс с открытыми ограничениями. Можно прочитать инструкцию, выполнить тесты и предложить конкретное улучшение. Нельзя пока честно сказать, что он увеличивает число задач на 20%, 50% или в несколько раз.

Самый полезный отзыв — пример, где навык помог избежать повторной работы или, наоборот, помешал закончить задачу. Такие наблюдения дают основание для узкой правки инструкции; десятки универсальных запретов обычно лишь утяжеляют её.
